大模型时代的产品设计：Prompt 即界面

2026-04-15 · MUZI-LI · 8 分钟阅读

过去二十年，我们做产品设计，本质是在设计界面：按钮放在哪、层级怎么分、流程走几步。用户通过"点击"告诉我们他要什么。

大模型把这件事悄悄改变了——用户开始用一句话描述他想要什么，而模型直接给出结果。界面在退后，意图在提前。

一、交互范式的迁移：从 GUI 到对话

传统的图形界面（GUI）依赖功能可见性：按钮长什么样，用户就知道能做什么。它的好处是确定、可预期；代价是，用户的意图被框死在预设的功能里。

对话式交互则相反：用户用自然语言表达意图，模型去理解并执行。它的好处是开放、灵活；代价是，输出不确定，用户不知道该"怎么问"。

所以成熟的产品往往是混合形态：常用、明确的操作仍保留按钮，开放、模糊的需求交给对话。两者不是替代，而是分工。

二、Prompt 即界面的几个设计原则

既然 Prompt 成了新的"界面"，那它也需要像设计界面一样被认真设计。

1. 给模型足够的上下文

模型不是你团队里那个"秒懂你"的同事，它需要你把背景、目标、约束都说清楚。模糊的输入，只会得到模糊的输出。

2. 明确约束与输出格式

直接告诉模型"输出 JSON""不要超过 200 字""分三条写"，比事后吐槽它"没按我说的来"有效得多。约束是 Prompt 的一部分，不是附加项。

3. 设计"失败体验"

对话式产品最容易被忽视的是失败路径：模型没听懂、答错了、或问了不该问的。好的设计会引导用户补充信息、提供可点击的示例、允许一键重试，而不是让用户面对一个冷冰冰的错误。

三、产品经理的新职责

当 Prompt 成为产品的一部分，产品经理的角色也在变：

  • 写 Prompt 规范：沉淀一套团队级的 Prompt 模板与最佳实践。
  • 建评估集：用一批有代表性的问题，持续检验 Prompt 的输出质量。
  • 把 Prompt 当资产：它有版本、要测试、要迭代，和代码一样需要被管理。

结语

"Prompt 即界面"不是一句口号，而是一种提醒：当用户不再点击按钮，产品的用户体验，就藏在你写下的每一句 Prompt 里。
